## Контракты (proposal)
```text
application(approved) 1─0..1 participation ─1 order ─* payment_event
                                  └─0..1 pass ─* scan
```
- `participation`: создаётся только из `applications.status=approved`, уникально по application; статусы reserved → confirmed → cancelled/expired.
- `order`: сумма и валюта берутся из тарифа на сервере, **никогда от клиента**; `idempotency_key`; статусы pending → paid → refunded/cancelled.
- `payment_event`: сырые события провайдера; уникальность по `provider_event_id` (replay = no-op); подпись проверяется до записи.
- `pass`/QR: только после `order.paid`.

## Контракты и тест-план 06 (из исходного плана; только спецификация, не реализация)

1. **Snapshot суммы.** Заказ фиксирует `amount_minor` (целые минимальные единицы) и `currency` (ISO 4217) в момент создания; последующая смена тарифа не меняет существующий заказ. Тест: изменить тариф после создания → сумма заказа прежняя.
2. **Expiry на сервере.** Резерв/заказ имеет `expires_at`; каждая операция (оплата, webhook, check-in) сверяет `now() > expires_at` сама, даже если cron-очистка опоздала. Тест: просроченный заказ без запуска cron → оплата не подтверждает место.
3. **Webhook.** Проверка подписи до разбора; сверка amount + currency + environment (test/live) + order id; повтор события (dedup по provider event id) и порядок событий (reorder: поздний `pending` не откатывает `paid`). Тесты: неверная подпись, чужая сумма/валюта/среда, дубликат, обратный порядок.
4. **Late payment.** Оплата после истечения резерва → статус `review`/автовозврат, место не выдаётся сверх capacity (no oversell). Тест: last seat занят, приходит поздняя оплата → refund/review, участников ≤ capacity.
5. **Refund.** Только staff с aal2 (MFA) и ключом идемпотентности; повтор с тем же ключом не создаёт второй возврат; изменённый payload с тем же ключом отклоняется. Тест: двойной клик/повтор.
6. **Check-in — отдельная модель.** Приглашение, заявка, одобрение, платёж, участие, QR и проход — разные сущности; check-in пишет отдельную запись (кто, когда, сканер, событие), повторный проход отклоняется. Тест: второй скан того же QR, скан сотрудником чужого события.
7. **Private address.** Адрес площадки не попадает в SSR/HTML публичных страниц и в общий API; выдаётся только участнику с подтверждённым участием через защищённый запрос. Тест: HTML `/events/:slug` не содержит адреса.
8. **Capacity / last seat.** Выдача места атомарна (блокировка или условный UPDATE); два параллельных запроса на последнее место → ровно один успех. Тест: конкурентная пара.

### B. Модель данных (раздельные сущности, ни одна не сливается с другой)
`reservation` · `participation` · `order` · `payment` · `payment_event` · `pass` · `checkin`.
- `reservation`: место под TTL (`expires_at`), привязано к событию и заявке.
- `participation`: факт участия; создаётся только из одобренной заявки и подтверждённой оплаты.
- `order`: снапшот `amount_minor` (целые минимальные единицы) + `currency` (ISO 4217) + `environment` на момент создания; сумма только серверная.
- `payment`: попытка/факт оплаты у провайдера; `provider`, `provider_payment_id`, `environment`, `status`.
- `payment_event`: сырое событие провайдера с `provider_event_id`.
- `pass`: QR, выпускается только после `order.paid`.
- `checkin`: отдельная запись прохода (кто, когда, сканер, событие).

**Уникальность:** `unique(provider, environment, provider_payment_id)`, `unique(provider, environment, provider_event_id)`, `unique(event_id, participation_id)`, `unique(order_id)` на `participation`, `unique(pass_id, checkin)` для однократного прохода. Идемпотентность заказов — ключ, привязанный к payload и событию (как уже сделано для заявок).

### C. Деньги и возвраты
- Поздняя оплата (после истечения резерва или при отсутствии места) → статус `needs_review`, место не выдаётся сверх capacity; далее контролируемый возврат.
- Автовозврат — **только предложение** в интерфейсе; выполняется после явного решения владельца.
- Повторный возврат: ключ идемпотентности + aal2; тот же ключ с изменённым payload отклоняется.
