# Билеты ВНЕ — инфраструктура выдачи, контракт 2

Статус: код и изолированные проверки готовы; подключение к целевому Supabase и рабочая выдача не активированы. Текущая реализация не отправляет email/Telegram и не принимает оплату. Ручная выдача гостю без аккаунта разрешена владельцем в этой задаче.

## Поток

Админка `/admin/tickets` → серверная функция с проверкой Origin, действующей staff-сессии, MFA aal2 и events_manage → отдельная Edge Function `vne-ticket-issuer` → узкие PostgreSQL RPC → существующие мероприятия, участия и заказы.

Сервис выдачи получает два независимых доказательства: секрет сайта и JWT сотрудника. В PostgREST передаётся именно JWT, никогда service_role. SQL повторно проверяет живые назначения и сессию. Тип карты GENERAL/VIP/ARTIST/SECURITY не даёт прав на сайте.

Личная ссылка `/pass#<view-token>` → единственный открытый POST `/api/tickets/read` → guest read issuer. Просмотр ничего не погашает. Токен не попадает в URL HTTP-запроса, Referer или журнал приложения. Сам HTTP POST содержит capability; тело не следует записывать в инфраструктурные логи.

Сканер `/scan`: назначенное мероприятие → камера или внешний сканер → `verify` → явное подтверждение `checkin`. Решение всегда принимает сервер. Нет offline-допуска и нет доверия к цвету/тексту карточки.

## Хранение

| Таблица | Назначение |
|---|---|
| public.events | Единственный источник мероприятия, вместимости, окна входа и времени выпуска QR |
| public.orders / participations / reservations | Существующий учёт оплаты, участия и резервов |
| private.ticket_passes | Билет, снимок имени/мероприятия/паттерна, версия, статус, два SHA-256 хеша |
| private.ticket_operations | Идемпотентные команды сотрудника; токенов в открытом виде нет |
| private.ticket_checkins | Одна запись прохода на билет, уникальность обеспечена БД |
| private.ticket_events | История выдачи, отзыва и проверок |
| D1 qr_pattern_versions | Существующая версионная библиотека оформления; не источник прав или допуска |

Все новые private-таблицы имеют RLS и закрытые прямые grants. Гость может вызвать только capability-wrapper `ticket_read`; доступ к private-схеме ему не выдаётся.

## Инварианты

- Одна блокировка мероприятия сериализует резервирование, ручную выдачу и конвертацию оплаты. Порядок блокировок event → order → participation/pass.
- Места: active participation + непросроченные active reservations + manual active/used + использованные participation-билеты, чьё участие уже отозвано/возвращено. Участия не считаются дважды.
- Отзыв ручного билета освобождает место. Использованный билет сохраняет место. Порядковый номер никогда не переиспользуется; номер может стать больше текущей вместимости после последовательных отзывов/перевыдач.
- Issue повторяется с тем же operationId и неизменным телом. При потерянном ответе получается прежний билет и прежняя личная ссылка.
- Revoke/checkin требуют expectedVersion. Уникальность checkin и транзакция защищают от повторного прохода; тот же operationId возвращает прежнюю квитанцию.
- Сканер повторно проверяет событие, живые права, срок, время открытия, статус оплаты/участия. Sandbox никогда не допускает вход.
- HMAC-SHA-256 создаёт разные 256-битные секреты view/scan из разных purpose-доменов. Ключ хранится только в issuer; в БД только хеши.
- Сервис сейчас поддерживает одну версию ключа. Не менять TOKEN_SECRET/TOKEN_KEY_VERSION пока действуют выпущенные билеты: сначала нужен key-ring либо организованная миграция.
- QR отображается только после qr_release_at. В билете сохранены рецепт и версия движка. При несовместимой версии либо неудачном decode художественного SVG показывается обычный проверяемый QR с тем же содержимым.
- Публичная карточка включается отдельно флагом VNE_TICKETS_PUBLIC_PASS=1. Открываются только GET/HEAD /pass и POST /api/tickets/read. Админка, сканер и остальные серверные функции остаются закрыты.

## API отдельного сервиса

POST `/api/admin/{catalog,list,issue,get,history,revoke}`; POST `/api/scan/{catalog,verify,checkin}`; POST `/api/pass/read`. `/health` показывает только версию контракта, это не проверка БД.

`issue`: eventId, name, access, reason, необязательные validUntil/design; UUID Idempotency-Key. Для существующего оплаченного участия дополнительно поддержан participationId. UI сейчас выпускает ручные приглашения, не создаёт фиктивные оплаченные заказы.

`checkin`: eventId, scan-token, expectedVersion, operationId. QR содержит `VNE1:<scan-token>`, не динамический рекламный редирект. Переназначаемые ссылки QR-студии и персональный допуск имеют разные назначения.
