# День 04. Supabase, авторизация и права доступа

**Цель:** создать серверный фундамент, на котором чужая заявка, чужой пропуск и административные действия недоступны обычному гостю.

**Обязательные вводные:** принятые результаты дня 03; подтверждённые репозиторий и рабочая ветка; идентификатор разрешённой тестовой среды Supabase либо возможность локального запуска. Доступы вводятся только через штатное управление секретами.

**Допустимый деморежим:** вымышленные пользователи и события, локальный почтовый перехватчик, тестовый домен. Реальную базу гостей сюда не копируем. Отсутствующий облачный доступ не заменяем автоматически созданным платным проектом.

**Ожидаемый результат:** воспроизводимые миграции, вход в кабинет, проверенная модель ролей, изоляция development и staging, начальный аудит и регламент резервирования.

**Порог перехода:** реальные проверки прав в тестовой БД пройдены. Если выполнены только файлы и макеты, день 05 можно проектировать, но серверную интеграцию принимать нельзя.

1. Установи фактические возможности среды.

Проверь доступный Supabase-проект, регион, тип размещения, существующую схему и миграции. Не выбирай боевое размещение и юрисдикцию вместо владельца. Не путай development, staging и production. Для каждого окружения нужны отдельные настройки, ключи, URL и тестовые данные. Если отдельного staging пока нет, опиши ограничение и подготовь конфигурацию; не называй одну общую базу двумя независимыми средами.

До реализации сверяй используемые API, CLI и Auth-подходы с текущей официальной документацией Supabase. Команды CLI узнавай через установленную версию и --help. Зафиксируй совместимые версии зависимостей в lockfile; не обновляй весь проект ради одной интеграции.

2. Подготовь минимальную модель данных.

Составь понятную схему связей: пользователь Auth, профиль участника, назначение сотрудника, событие, заявка, право участия, заказ, событие платежа, пропуск, проход, журнал аудита, очередь уведомлений. Сегодня реализуй основу и ограничения, необходимые для следующих дней; не добавляй десятки пустых таблиц для гипотетических возможностей.

Профиль участника не должен содержать редактируемое пользователем поле, которое даёт административные полномочия. Роли и назначения храни в защищённой модели; сотрудник получает права на конкретное событие и срок. Создание первого владельца выполняется отдельной контролируемой процедурой, не регистрацией через публичную форму. Отдельные конфиденциальные сведения помести в закрытую область данных с минимальными разрешениями.

Миграции должны воспроизводиться из Git. Сначала проверь изменения в изолированной локальной или разрешённой тестовой базе, затем подготовь чистую миграцию штатным инструментом. Не применяй разрушительный reset к подключённому удалённому проекту. Предоставь seed только из явно вымышленных записей, включая минимум двух гостей и сотрудников с разными правами.

3. Реализуй Auth и жизненный цикл сессии.

Добавь вход, выход, восстановление доступа и защищённую оболочку /member. Используй текущий поддерживаемый способ проверки сессии на сервере. Возврат после входа разрешай только на проверенные внутренние маршруты; исключи открытое перенаправление на произвольный URL. Покажи понятные состояния просроченной ссылки, неверного кода и недоступной сети без раскрытия лишних сведений о существовании аккаунта.

Определи MFA для сотрудников /admin и /scan и серверную проверку требуемого уровня сессии. Если MFA пока невозможно проверить, обозначь это блокировкой приёмки административного доступа. Снятая роль должна прекращать критические операции без ожидания обновления интерфейса. Не используй user_metadata для авторизации; учти, что роли в JWT могут устаревать. Проверяй актуальные назначения в доверенной серверной операции.

4. Настрой доступ на уровне БД и API.

Проверь exposed schemas, GRANT и RLS отдельно. Каждая доступная через Data API таблица должна иметь осмысленные политики, а не общий доступ всем authenticated. Гость читает только принадлежащие ему записи. Изменения проверяют и прежнего владельца, и допустимое новое состояние через USING/WITH CHECK. Добавь отрицательные тесты, где гость меняет user_id, роль, цену или чужой идентификатор.

По умолчанию используй минимальные права и SECURITY INVOKER. SECURITY DEFINER допускается только для обоснованной узкой операции: фиксированный search_path, проверка вызывающего и полномочий, ограниченные аргументы, явное управление EXECUTE. Проверь REVOKE EXECUTE FROM PUBLIC и разрешения anon/authenticated; закрытое имя функции само по себе ничего не защищает. Представления должны сохранять ограничения доступа, например через поддерживаемый security_invoker, либо быть закрыты от публичных ролей.

Публичный SSR и данные главной содержат только публичную информацию. Частные маршруты и ответы не должны попадать в общий HTML, публичный JSON, CDN-кэш или поисковую индексацию. Не размещай service_role/secret key в браузере. Используй серверные секреты только там, где действительно нужна привилегия.

5. Начни эксплуатационный фундамент сейчас.

Создай минимальный аудит привилегированных действий с актором, временем, объектом, результатом и correlation ID, без паролей и содержимого токенов. Подготовь outbox для последующих уведомлений, но не отправляй сообщения наружу. Раздели публичные материалы и закрытые файлы Storage, опиши политики и ограничения загрузки. Определи резервирование БД и отдельных объектов Storage, владельца процедуры и изолированную площадку восстановления. Репетиция будет в день 09, но необходимые настройки и ограничения зафиксируй сегодня.

6. Проверь результат и честно обозначь границы.

Выполни сборку, проверку типов и релевантные проверки проекта. В настоящей тестовой БД проверь anon, гостя А, гостя Б, сотрудника своего события, сотрудника другого события и сотрудника со снятым назначением. Подтверди отказ на чтение и изменение чужих записей, повышение роли и вызов привилегированной RPC. Проверь MFA и выход из сессии. Сохрани результаты без секретов.

Если изменения ещё не закоммичены, так и напиши; не придумывай итоговый SHA. День 05 автоматически не запускай.
