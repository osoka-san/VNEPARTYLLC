# ВНЕ — план из 10 рабочих итераций и инструкция к промптам

Подготовлено 23.09.2026 для [VNE Portal](https://lovable.dev/projects/7e261ce4-c261-40b6-b169-b9806a6e37d7).

В пакете: **10 самостоятельных промптов**, аудит этапа 1.1, PNG-схема и два снимка фактически обнаруженной ошибки. Аудит относится к SHA `557526cd0998ca342e96b92b9611bd17d2e17d37`. Промпты ещё не выполнялись; код сайта и базы в рамках подготовки пакета не изменялись.

## Какой результат планируем

Цель спринта — **проверенная тестовая версия полного пути**: сайт → заявка → решение команды → кабинет → тестовый заказ → событийный QR → регистрация входа → управление и восстановление.

10 пунктов — зависимые рабочие итерации. При готовых вводных их можно распределить на 7–10 рабочих дней. Это плановая рамка, а не обещание закончить весь безопасный production за десять календарных дней. Работа с правами БД, платежами, конкурентным входом и восстановлением может потребовать больше времени. Непройденный критерий переносит зависимый этап.

Текущий этап 1.1 не принят: в доступном браузере при недоступном WebGL не появился SVG fallback. Поэтому начинаем с точечного исправления, а не наращивания возможностей поверх непроверенного первого экрана.

## Три рубежа приёмки

**После 03 — визуальная часть.** Первый экран не ломается без GPU, все публичные страницы доступны, мобильная навигация работает, сохранён бренд. До этого можно обсуждать серверную схему, но нельзя считать внешний сайт принятым.

**После 07 — данные и допуск.** Проверены настоящие серверные права, принадлежность записей, конкурентность и однократный первичный проход. Красивый QR без этих проверок не означает готовность входа.

**После 10 — решение о запуске.** Есть репетиция на staging, измеренное восстановление, список остающихся задач и конкретный состав версии. Реальные гости, деньги и рассылки включаются отдельным решением после необходимых проверок.

## Как работать с файлами

1. Распакуй ZIP и открой папку `prompts`. Начни с `01_Stage_1_1_Acceptance.md`.
2. Открой существующий проект VNE Portal, а не новый проект. Проверь фактически связанную ветку GitHub. Папка Audit Pack в `public` сама по себе не доказывает, что приложение синхронизируется с этой веткой.
3. Для дня 01 приложи аудит. Исходные SVG/шрифты прикладывай повторно только если их нет в текущем репозитории или Lovable сообщает точные отсутствующие файлы.
4. Прочитай вводную над блоком: цель, исходные данные, ожидаемый результат и условие перехода. Затем скопируй **весь блок `text`** из одного файла в Lovable.
5. Если используешь режим планирования, сначала проверь предлагаемый объём и список изменений, затем запусти реализацию этого же этапа. Не отправляй все десять промптов одной командой на автоматическое выполнение.
6. После выполнения открой preview и отчёт `docs/sprint/day-XX-report.md`. Проверь именно критерии текущего дня. Просьба «проверь всё» менее полезна, чем конкретный сценарий из файла.
7. При FAIL попроси исправить замечание в рамках текущего этапа и повторить соответствующую проверку. При NOT VERIFIED выясни, каких доступа, устройства или данных не хватает. Следующий зависимый этап не становится принятым автоматически.
8. Переходи к следующему файлу после приёмки. В каждом следующем промпте уже есть требование прочитать отчёт предыдущего дня.

**Значения статусов:** PASS — реально проверено и работает; FAIL — проверено и не работает; NOT VERIFIED — не проверено; BLOCKED — зависимость не позволяет завершить проверку или интеграцию.

Не нужно в каждый день заново переносить весь контекст диалога. Каждый файл повторяет проект, стек, бренд, границы задачи, критерии и формат отчёта. При потере контекста источником истины становятся актуальный код и сохранённые отчёты.

## Архитектурные решения этого спринта

- Текущий TanStack Start + React + TypeScript + Three/R3F сохраняется. Главная атмосферная; /member, /admin и /scan — лёгкие рабочие интерфейсы.
- Один основной Supabase/PostgreSQL-контур на среду содержит транзакционно связанные заявки, участие, заказы, пропуски и проходы. Несколько независимых БД не участвуют в одной операции допуска. Отдельные dev/staging/production — отдельная задача изоляции, а не три названия одной базы.
- Публичный QR кампании, постоянная карта и событийный пропуск — разные сущности. Постоянная карта не выдаёт автоматический проход.
- Выдача и проверка QR — серверные операции; первая регистрация входа выполняется атомарно в БД. Отдельный большой сервер не нужен только ради рисования QR-картинки; способ размещения API выбирается по существующей инфраструктуре.
- Auth, GRANT, RLS и серверные назначения определяют доступ. Скрытая кнопка не является защитой. Этот подход соответствует [официальному руководству Supabase по Data API](https://supabase.com/docs/guides/api/securing-your-api).
- Backup БД и копии объектов Storage учитываются отдельно: [документация Supabase](https://supabase.com/docs/guides/platform/backups) прямо указывает, что объекты Storage не входят в резервную копию БД. В пакет включена фактическая репетиция восстановления, а не только зелёный индикатор.
- Текущий публичный MCP сайта остаётся справочником бренда. Он не превращается в открытый канал выдачи QR, чтения гостей или изменения БД.

## Что сознательно остаётся после спринта

Полный бесшовный бесконечный цикл главной; физические карты и их жизненный цикл; Wallet/NFC; распределённый offline-вход; live-платежи и фискализация; расширенная аналитика; нагрузочная подготовка под подтверждённую вместимость; production-публикация.

Конечная главная сохраняет художественные переходы. Бесконечный цикл добавляется после того, как работают прямые ссылки, Back, клавиатура, формы, resize и reduced motion. Его не стоит вводить крупной новой функцией в день итоговой приёмки.

## Как уместить в семь рабочих дней

Только при заранее готовых доступах и отсутствии блокеров можно объединить расписание: 01; 02+03; 04; 05; 06; 07+08; 09+10. Промпты при этом выполняются последовательно и сохраняют отдельные критерии. Если проверки не укладываются, расширь спринт вместо пропуска тестов.
