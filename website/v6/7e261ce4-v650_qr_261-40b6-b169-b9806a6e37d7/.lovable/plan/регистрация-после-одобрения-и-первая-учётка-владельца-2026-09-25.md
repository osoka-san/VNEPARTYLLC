# Регистрация после одобрения и первая учётка владельца

## Результат

Посетитель оставляет настоящую заявку на участие без создания аккаунта. После одобрения сотрудником система отправляет одноразовое email-приглашение: пользователь задаёт пароль, получает профиль и входит в личный кабинет. Самостоятельная открытая регистрация остаётся закрытой.

Для `savik3003@gmail.com` будет создана первая учётка с максимальной ролью `owner` (в интерфейсе — владелец/администратор). Пароль не создаётся и не передаётся: владелец получает письмо, сам задаёт пароль и подключает TOTP перед доступом в `/admin`.

## Что будет изменено

1. **Заявка до регистрации**
   - Перевести `/apply` из явно обозначенной демо-проверки в реальную форму заявки: имя, email, обязательный Telegram и выбранный интерес/событие.
   - Добавить отдельное защищённое хранилище заявок на членство; не смешивать их с существующими заявками авторизованных пользователей на события.
   - Не давать браузеру прямой доступ к персональным данным: публичная отправка идёт через валидируемую серверную функцию, чтение и решения доступны только сотрудникам с действующей сессией и MFA.
   - Добавить ограничения длины, нормализацию email/Telegram, honeypot и серверное ограничение частоты; одинаковый безопасный ответ не раскрывает существующие аккаунты или повторные заявки.

2. **Одобрение и приглашение**
   - Сделать в `/admin` рабочий раздел «Заявки»: список, состояния, одобрение и отклонение.
   - Каждое решение повторно проверяет на сервере действующую staff-сессию, `aal2` и роль; клиентская страница не является границей безопасности.
   - Одобрение создаёт/находит учётку только на сервере, отправляет одноразовое приглашение и атомарно фиксирует результат/аудит. Повторное нажатие не создаёт дубликат и не выдаёт лишние права.
   - Одобрение обычной заявки создаёт только профиль участника. Роли команды и администратора никогда не берутся из формы или метаданных регистрации.

3. **Активация аккаунта**
   - Расширить публичный callback для invite-ссылок и добавить экран первичной установки пароля с безопасным redirect в `/member`.
   - Сохранить текущие fail-closed правила, `private/no-store/noindex`, безопасные redirect, disabled до загрузки, единые сообщения об ошибках и существующие recovery/login/Telegram потоки.
   - На `/login` и в уместных CTA показать путь «Оставить заявку» вместо открытой кнопки signup; после одобрения пользователь регистрируется только по письму.
   - Профиль продолжает создаваться существующим серверным триггером; после входа пользователь может заполнить отображаемое имя и привязать Telegram.

4. **Первая учётка владельца**
   - Через одноразовую серверную операцию отправить приглашение на `savik3003@gmail.com`, затем назначить созданному пользователю единственную максимальную роль `owner` существующим операторским bootstrap-механизмом.
   - Перед операцией повторно проверить, что адрес и активный owner отсутствуют; сейчас живая база подтверждает: пользователей `0`, активных owner `0`.
   - Не хранить временный пароль, не добавлять публичный bootstrap endpoint и не помещать роль в профиль/JWT/localStorage.
   - После активации доступ в `/admin` всё равно потребует настройку TOTP, как требует текущая модель прав.

5. **Настройки входа и письма**
   - Оставить свободную регистрацию выключенной, анонимный вход выключенным и автоподтверждение выключенным; email/password должен быть включён для входа, приглашений и восстановления.
   - Включить проверку утёкших паролей и требование текущего пароля для последующей смены пароля.
   - Сейчас собственный email-домен не настроен, поэтому приглашение будет отправлено стандартным отправителем Lovable. Брендированные письма в эту задачу не входят.

## Технические детали

- Новая миграция добавит `membership_requests` и приватные данные rate-limit/audit с точными `REVOKE`/`GRANT`, RLS и без доступа `anon` к таблице заявок.
- Серверные функции будут разделены на публичную отправку и защищённые staff-операции; привилегированный клиент загружается только внутри обработчика после проверки роли.
- Схема заявки не будет ссылаться на пользователя до приглашения; после создания аккаунта сохраняется связь с ним и состояние приглашения.
- Существующие `profiles`, `staff_assignments`, `private.bootstrap_first_owner`, `my_staff_access`, MFA и Telegram остаются источниками истины и не дублируются.
- Обновятся типы, документация и архитектурное правило о закрытой регистрации после одобрения.

## Проверки

- Unit: валидация/нормализация, одинаковые ответы, безопасные redirect, повторное одобрение и запрет самовыдачи ролей.
- База: grants/RLS, anon не читает заявки, staff без MFA/назначения отказан, owner с `aal2` видит и решает, обычное одобрение не создаёт staff-role.
- Живой сценарий: отправка заявки → просмотр owner → одобрение → письмо → установка пароля → профиль → MFA → `/admin`; отдельно отказ, повторное одобрение, просроченная/повторная ссылка и logout.
- Typecheck, затронутый lint, unit/integration, build и Chromium на телефоне/desktop; отчёт честно пометит недоступные проверки.
- База/Auth меняются только после одобрения этого плана. Production publish не выполняется.
