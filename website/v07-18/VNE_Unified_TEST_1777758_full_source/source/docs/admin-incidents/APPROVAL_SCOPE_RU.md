## Минимальная схема и API

1. Новый закрытый private.vne_incident_session_ok, без EXECUTE для API-ролей.
2. Ранее согласованные четыре private-таблицы истории нарушений/решений/идемпотентности/R2-ревью, закрытые функции и представление. Три исходных SQL-файла используют усиленный guard.
3. Три узких названия ролей: incident_operator, incident_manager, membership_reviewer. Назначаются только две последние выбранному ADMIN_TEST; новым сотрудникам права не выдаются.
4. EXECUTE для authenticated только на восемь точных public RPC: vne_incident_context(), vne_incident_lookup(uuid,text,text), vne_incident_read(uuid,uuid,uuid), vne_incident_record(jsonb), vne_incident_append(jsonb), vne_intake_list(text,integer), vne_intake_read(uuid), vne_intake_review(jsonb). Все проверяют отдельную роль, текущую живую AAL2-сессию, factor и staff prerequisite. Таблицы, private schema, anon/service_role остаются закрыты.
5. После личной MFA-настройки и нового точечного readback создать только выбранному UUID служебный member_admission=exempt, incident_manager для всех текущих/будущих мероприятий TEST и membership_reviewer общих R2-анкет, до отзыва. Это снимает общий служебный gate и открывает соответствующие истории, контакты и ответы. Приглашение, билет и event admission не создаются.

Патч перенесён на опубликованное исправление MFA TEST v9, commit76151bcb64e79c0a808dba2b491db736d60d3c66. Перед публикацией нужно повторно сверить актуальный source и сохранить любые более новые одобренные изменения. Патч не является готовым разрешением перезаписать TEST v9.

Гостевые и scanner-аккаунты не допускаются новым внешним TEST-guard к этим маршрутам; только выбранный ADMIN_TEST. Сервер и БД всё равно проверяют реальные роли и AAL2. Режим VNE_INCIDENTS_MODE=test отдельно включается при публикации; по умолчанию закрыто. Контакты/ответы загружаются только при раскрытии конкретной анкеты. Выход в любой вкладке очищает показанные данные и блокирует устаревшие ответы. CMS/D1-админка не открывается.

Сотрудник фиксирует факты и запрос; менеджер решает отдельно. 90-дневное решение пока не связано с Auth-блокировкой, билетами или проходом; не описывать его как уже действующий запрет входа.

## Порядок и подтверждение

Сначала исправить личную MFA-настройку и получить реальное подтверждение фактора/AAL2. Затем независимое ревью точных SQL+UI хешей, проверка актуального TEST-source и владельцев/тел/ACL prerequisite-функций. После этого одно точное подтверждение владельца на перечисленные DDL, 8 RPC, публикацию двух страниц/transport/флага и два назначения со staff-exempt. Сам запрос «выдай права, пункт 3» не подменяет это уточнение нового постоянного API-доступа.

Закрытый assignment SQL намеренно прерывается на PENDING_OWNER_ACTION_TIME_APPROVAL. При любом уже появившемся назначении/допуске, ошибке личности/MFA или audit write он прерывается; доступ не удваивается и существующие записи не перезаписываются. Финальное применение выполняется только после разрешения, а не запуском файла как есть.
